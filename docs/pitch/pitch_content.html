Part 1 — Team-Member Explainer

Short, beginner-friendly. For a teammate who hasn't read the specs.

Right now, the ambulance, the route, and the hospital for an emergency get picked almost separately — so a patient can end up at a hospital with no bed ready for them. Our project connects all three into one system: it picks the right ambulance, the fastest route, and a hospital that has actually agreed to take the patient and has a bed held and waiting. If anything changes on the way — traffic, a lost bed, a broken-down ambulance — it automatically re-checks everything, live. The hospital data in our demo is simulated and clearly labelled as such; everything else is real and working end to end.

Part 2 — Judge Pitch

Full spoken content, in presentation order. Beginner-friendly, persuasive, and honest about limits.

1. The Problem

Every year, precious minutes are lost in emergencies — not because ambulances are slow, but because of something less visible: bad coordination. An ambulance can be sent that isn't equipped for the patient's actual condition. It can be routed to the nearest hospital, only for that hospital to have no ICU bed free, or to reject the patient on arrival — forcing a second, more dangerous journey while the clock keeps running.

Today, four decisions — which ambulance, which route, which hospital, and whether a bed is actually ready — are handled as separate, disconnected steps. Our project treats them as one decision, made together, and kept up to date as things change.

2. Our Idea (Overview)

The Smart Ambulance Routing & Emergency Bed Allocation System is a coordination platform that manages the entire emergency journey — from the moment a call comes in, to a hospital bed being physically ready for the patient.

Given an emergency and the patient's needs, the system doesn't just find the nearest ambulance and nearest hospital. It:

  • finds the ambulance that is actually free and equipped for this specific patient;
  • calculates the fastest reliable route, not just the shortest one;
  • filters hospitals down to the ones that can medically handle the case;
  • ranks those hospitals by real capability and likelihood of acceptance;
  • gets that hospital to explicitly say yes; and
  • reserves the exact resource — an ICU bed, a ventilator, a trauma bay — before the ambulance ever arrives.
Nearest is not necessarily fastest.
Fastest is not necessarily suitable.
Suitable is not necessarily accepting.
Available now is not necessarily available on arrival.

We built the whole system to solve for the best feasible chain — not the closest single point.

3. How It Works

Emergency reported → patient needs captured (e.g. "ICU required", "trauma required") → ambulances scored on suitability, availability & ETA → best ambulance assigned → real route calculated, with alternatives considered → hospitals filtered by medical capability and current resource state → hospitals ranked → hospital staff explicitly accept or reject on their own dashboard → on acceptance, the specific resource is reserved — server-side, transaction-locked, so two ambulances can never claim the same bed → the mission is tracked live over a real-time connection → if conditions change, the system automatically reassesses and can re-route or re-rank → the hospital gets advance notice to prepare → patient arrives at a hospital that is ready and waiting.

Two things make this trustworthy rather than a black box: every recommendation comes with a plain-language explanation of why that ambulance or hospital was chosen, and a human dispatcher can override any decision at any time. The system never invents a recommendation when nothing genuinely qualifies — it says so instead.

4. Tech Stack

Frontend — what dispatchers, hospitals and crews actually see

React + TypeScriptViteTailwind CSS TanStack QueryZustandReact Router React Hook Form + ZodRecharts

Three live screens — dispatcher, hospital, and ambulance crew — plus a demo controller, built quickly and kept type-safe with React/TypeScript on Vite. TanStack Query and Zustand keep every screen automatically in sync with the live backend instead of needing manual refreshes; React Hook Form and Zod validate inputs (like patient requirements) before they ever reach the server.

Backend — the decision-making brain

PythonFastAPIPydantic SQLAlchemyAlembicWebSockets

FastAPI runs all the matching, ranking, and business rules, with Pydantic validating every request. SQLAlchemy and Alembic manage the database schema safely as it evolves. WebSockets push live updates — a hospital accepting, a bed being reserved, a route changing — to every open screen instantly.

Database — where location actually matters

PostgreSQLPostGIS

PostGIS is a real spatial database extension, so "which ambulance/hospital is actually near this incident" is a genuine geographic calculation, not a rough approximation.

Optimization & AI — used only where they earn their place

Google OR-ToolsXGBoost / LightGBMscikit-learn

OR-Tools is available for the matching layer where a proper solver beats simple sorting. XGBoost/scikit-learn power an optional arrival-time prediction layer — used only where a prediction genuinely improves a decision, and never used to claim an accuracy number we haven't actually measured.

Testing — proving it works, not just claiming it

PytestVitestReact Testing LibraryPlaywright

Backend logic, frontend components, and full real-browser flows are all covered by automated tests (results in the Feasibility section below).

6. Implementation Process

The system was built in a fixed phase order, and each phase had to produce a genuinely working output before the next one started — nothing was designed in isolation and stitched together at the end:

PhaseWhat it delivered
FoundationRepository, auth, base UI — a running application
Core data modelIncidents, ambulances, hospitals, resources, reservations, missions
Ambulance matchingCapability + availability + ETA scoring → working ambulance selection
RoutingReal route calculation with alternatives → working map
Hospital matchingCapability + resource filtering → ranked, explained recommendation
AcceptanceHospital dashboard with accept/reject/timeout → confirmed destination
ReservationTransactional hold/confirm/release/expiry → safe resource reservation
Real-time coordinationWebSockets, live state, dynamic re-ranking → a truly live mission
Failure simulationTraffic change, ICU loss, hospital rejection, ambulance/GPS failure → stress-tested live
AI layer (optional)ETA prediction with confidence, added only after everything else worked
QA & demo rehearsalFull scenario validation and presentation polish

This order was deliberate: get one complete, real, end-to-end emergency working first, then layer on real-time behaviour, failure handling, and AI — never the reverse.

7. Practicality — Making This Real

The architecture was designed for the handoff to production from day one, not bolted on afterward:

  • A clean integration seam is already built in. Hospital data sits behind an integration interface. Moving from simulated hospital capacity to a real, authenticated hospital feed is a matter of plugging in an adapter — not redesigning the core system.
  • The security and audit basics real partners ask for first are already in place — role-based access control, authenticated real-time connections, and an audit trail of every critical decision.
  • Double-booking is already impossible, because reservations are server-side, transaction-locked, and database-enforced — this is the piece hospitals and regulators would scrutinize hardest, and it's proven, not promised.
  • A realistic rollout path: pilot in a single city or district with a small set of partner hospitals; swap their data from simulated to a live feed through the existing adapter once an integration agreement is signed; expand ambulance and hospital coverage gradually from there.
  • The production evolution is mapped, not hand-waved — from today's single backend service to dedicated dispatch, hospital, routing, ML and reservation services connected to real hospital systems, ambulance tracking (AVL), traffic providers, and emergency-response infrastructure.
What this prototype cannot yet validate Real clinical outcomes, actual mortality impact, live nationwide hospital integration, hospital cooperation at scale, and performance under real emergency-traffic load. We say this plainly rather than implying it's already solved — the roadmap above is how we'd close each gap.

8. Why It Matters

Every part of this system exists because emergencies are won or lost on minutes, and today those minutes get wasted on decisions made separately: the right ambulance sent to the wrong hospital, or the right hospital found too late to get ready. We built the coordination layer that closes that gap.

"We're not just moving an ambulance. We're getting a patient to a hospital bed that is medically right, has already said yes, and is already waiting for them."
